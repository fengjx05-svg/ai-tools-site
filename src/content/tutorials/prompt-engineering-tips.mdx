## 核心概念：Prompt 工程 ≠ 会说话

很多人以为 Prompt 工程就是"把话说清楚"。这个理解对了一半。

2026 年的 AI 模型（Claude Sonnet 4.5、GPT-5）理解力已经非常强，你觉得"说清楚了"，它们确实理解了。但它们缺的不是理解力，而是**上下文**。

**好的 Prompt = 给足上下文 + 给清约束 + 给对示例**。下面 10 个技巧按使用频率排列，从基础到进阶。

## 10 个实战技巧

### 1. 给上下文，而不是给命令

❌ "帮我写个登录功能"

✅ "这个项目是 Next.js 15 + NextAuth v5 + Prisma。用户表在 @schema.prisma 里有 email/password/role 三个字段。帮我用 NextAuth 的 Credentials Provider 实现登录 API，返回 JWT 里要包含 role 字段。参考 @src/lib/auth.ts 里的现有配置。"

**为什么有效**：AI 不知道你项目里有什么。你不告诉它，它就猜。给上下文的三个核心要素：
- 技术栈（框架、库、版本）
- 相关文件（用 @ 引用）
- 输出期望（要什么格式、放哪个目录）

### 2. 用 Pseudo-Code 精准描述逻辑

当你知道想要什么逻辑但不想手写实现时，用伪代码描述：

```
我要一个函数，逻辑如下：
1. 接收 userId 和 newEmail
2. 查数据库确认 newEmail 没被占用
3. 如果被占用，返回 { success: false, reason: "email_taken" }
4. 如果没被占用，生成一个 6 位数字验证码，有效期 10 分钟
5. 把验证码存到 Redis（key = "verify:{userId}"）
6. 发验证邮件
7. 返回 { success: true, expiresIn: 600 }
```

伪代码比自然语言精确，比真实代码省时间。这是效率和准确率的平衡点。

### 3. 增量式 Prompt（一次只让 AI 做一件事）

❌ "帮我把整个模块重构完"

✅ 分三步：

```
第 1 步："先列出 auth 模块需要重构的文件清单，按依赖关系排序。不要写代码。"
第 2 步："重构第 1 个文件 src/lib/auth.ts。改动范围：提取 JWT 逻辑到独立函数。"
第 3 步："重构第 2 个文件。注意刚才第 1 个文件改了 JWT 的导出名，这里要对应。"
```

**数据支撑**：AI 的一次性任务成功率与任务范围成反比。单文件改动准确率约 85%，跨 5 文件以上的任务跌到 50% 以下。

### 4. Constitutional Prompting（定规矩）

在项目根目录创建 `CLAUDE.md` 或 `.cursorrules`，写入项目级的"规矩"：

```markdown
## 编码规范
- 所有函数必须显式声明入参和返回值类型（TypeScript）
- 不做默认导出（export default），始终用命名导出
- 错误处理：API 层返回 `{ success: false, error: string }` 格式
- 数据库查询使用 Prisma，禁止 raw SQL
- 文件不超过 300 行，超过即拆分
- 不引入新依赖，除非先征求同意
```

规矩写好一次，每次新会话 AI 都自动遵守。**这是投入产出比最高的 Prompt 技巧。** 2026 年 Thoughtworks 的技术雷达已将"团队共享 AI 指令文件"列为推荐实践。

### 5. 示例驱动（给输入/输出对）

❌ "写一个把日期字符串转成友好格式的函数"

✅

```
写一个日期格式化函数：

输入/输出示例：
"2026-05-12" → "2026 年 5 月 12 日"
"2026-01-03" → "2026 年 1 月 3 日"
null → "--"
"invalid" → "--"

要求：TypeScript，不依赖第三方库。
```

给 2-3 个具体例子，比写一长段文字描述更准确。例子消除歧义，AI 直接知道你要什么。

### 6. 禁止清单（告诉 AI 不要做什么）

很多时候，说清楚"不要什么"比说清楚"要什么"更重要：

```
要求：
- ❌ 不要用 any 类型
- ❌ 不要引入新的 npm 包
- ❌ 不要修改已有 API 的返回格式
- ❌ 不要删除现有的注释
- ❌ 生成的代码里不要有 console.log
```

这在重构或维护现有项目时尤其重要。AI 喜欢"顺手优化"不相干的东西，禁止清单能约束它。

### 7. 先 Plan 再 Implement

这是 Cursor 和 Claude Code 用户的共识工作流：

```
第 1 轮（Plan）：
"我想给用户系统加上两步验证（2FA）。先分析现有代码，告诉我：
- 需要改哪些文件
- 每个文件改什么
- 依赖的第三方库
- 数据库 schema 变更
不要写代码。"

第 2 轮（Review Plan）：你人工审查方案，修正 AI 的假设

第 3 轮（Implement）：
"按照上面方案实现。每次改完一个文件暂停，让我审查。"
```

**Plan 阶段花 5 分钟，能省 Implement 阶段 30 分钟的返工。**

### 8. 用 @ 引用给 AI "指路"

Cursor 和 Claude Code 都支持引用系统：

| 引用方式 | 用途 | 示例 |
|----------|------|------|
| `@Files` | 让 AI 读特定文件 | `@src/utils/format.ts 在这个文件里加上处理空值的逻辑` |
| `@Folders` | 让 AI 了解目录 | `@src/components 检查所有组件的 props 是否有遗漏的类型` |
| `@Codebase` | 全局搜索 | `@Codebase JWT 验证逻辑在哪些文件里？` |
| `@Web` | 实时搜索 | `@Web Next.js 16 的 Server Actions 有什么变更` |
| `@Git` | 看提交历史 | `@Git 上周谁改了 auth.ts？改了什么？` |

**核心原则**：不用引用 = AI 盲猜你的代码。用了引用 = AI 基于真实代码回答。准确率差距在 30% 以上。

### 9. 角色扮演和复核

```
"你是一个有 10 年经验的 TypeScript 全栈工程师。实现完成后，请你自己 Review 一遍代码，检查：
1. 是否有 SQL 注入风险
2. 是否有 XSS 风险
3. 边界情况（空值、超长输入、并发请求）
4. 是否有类型安全问题
5. 错误处理是否完整
把检查结果附在代码后面。"
```

角色扮演让 AI 更倾向于采用该角色的思维模式。"自我复核"指令让 AI 在给出答案前多一轮自我检查，减少低级错误。

### 10. 分层实现（Layer by Layer）

复杂功能不要一次给完所有细节，而是一层一层加上去：

```
第 1 层：功能裸跑
"实现基础的创建文章 API，POST /api/articles，接收 title + content，存数据库，返回文章 ID。不考虑权限和验证。"

第 2 层：加验证
"加上用 Zod 做输入验证，title 1-200 字符，content 非空。"

第 3 层：加权限
"加上身份验证，只有登录用户可以创建文章，文章关联到创建者的 userId。"

第 4 层：加边界处理
"处理重复标题、超长内容、并发创建等边界情况。"

第 5 层：加测试
"为上面的实现写单元测试和集成测试。"
```

每层产出独立可审查，出问题容易定位。比一次性丢出全部需求、最后得到一个"不知道哪里不对"的结果强太多。

## 常见反模式：这些做法已经过时了

2026 年，这些 Prompt 技巧不再有效甚至有害：

| 过时做法 | 为什么失效 |
|----------|-----------|
| "Think step by step" | 现代推理模型（o4-mini、Claude Extended Thinking）已经内置推理链，额外要求只会增加响应时间 |
| "我给你 $200 小费" | 对 2026 年的前沿模型没有一致效果。格式比情绪更重要 |
| 一次给 8+ 个示例 | 会导致"少样本崩塌"，过多示例反而让准确率从 64% 跌到 33% |
| 过度复杂的 Prompt 模板 | 对 GPT-5、Claude Opus 等顶级模型，简单直接的指令效果更好 |
| "你是 xxx 领域 20 年专家" | 不提升事实准确性，可能引入偏见 |

## 实用 Prompt 模板

### 功能开发模板

```
技术栈：[框架、语言、关键库]
现有代码参考：@[相关文件路径]
需求：[一句话描述]
具体要求：
- 输入：[参数类型和格式]
- 输出：[返回值格式]
- 错误处理：[错误场景和处理方式]
- 不要：[禁止事项]
示例：[1-2 个输入输出对]
```

### Bug 修复模板

```
Bug 描述：[现象]
复现步骤：[1. 2. 3.]
相关文件：@[文件路径]
预期行为：[应该怎样]
实际行为：[实际怎样]
已排查：[已经排除的原因]
```

### 代码审查模板

```
审查文件：@[文件路径]
重点关注：
1. 安全问题
2. 性能问题
3. 边界情况
4. 类型安全
5. 代码可读性
不要只给结论，每个问题给出具体代码位置和修改建议。
```

## 总结

| 技巧 | 难度 | 效果 | 一句话 |
|------|------|------|--------|
| 给上下文 | 入门 | ⭐⭐⭐⭐⭐ | 告诉 AI 你的项目长什么样 |
| 伪代码描述 | 入门 | ⭐⭐⭐⭐ | 逻辑精准、省时间 |
| 增量式 Prompt | 入门 | ⭐⭐⭐⭐⭐ | 一次一件事，准确率高 |
| Constitutional Prompting | 中级 | ⭐⭐⭐⭐⭐ | 规矩写一次，每次都管用 |
| 示例驱动 | 入门 | ⭐⭐⭐⭐ | 2-3 个例子比一段文字更准 |
| 禁止清单 | 入门 | ⭐⭐⭐⭐ | 告诉 AI 别碰什么 |

**核心认知**：2026 年的 Prompt 工程已经不再是"学会几个魔法词汇"。真正的竞争力在于 **上下文管理**——用 `CLAUDE.md`/`.cursorrules` 建立项目级规矩，用 @ 引用让 AI 看到真实代码，用 Plan→Implement→Review 三步法控制任务复杂度。

把 AI 当成一个新加入团队的聪明同事：你不给够背景信息，它猜不准；你不拆分任务，它做不完；你不对齐验收标准，它做不对。

## FAQ

### 哪个技巧最立竿见影？

给上下文（技巧 1）和 @ 引用（技巧 8）。不改变任何习惯，只是在每次提问前多花 10 秒告诉 AI 你的项目环境，准确率就能从 60% 级别跳到 80% 级别。

### CLAUDE.md 和 .cursorrules 有什么区别？

本质一样，都是项目级指令文件。CLAUDE.md 用于 Claude Code，.cursorrules 用于 Cursor。都可以写编码规范、项目结构说明、禁止事项。如果你两个工具都用，可以维护一份内容，两个文件同步。

### 我需要把所有技巧都用上吗？

不需要。从技巧 1（给上下文）、技巧 3（增量式）、技巧 4（写规矩文件）开始。这三个覆盖了 80% 的提效空间。其余技巧在遇到特定场景时再学。

### 这些技巧对中文 Prompt 也有效吗？

完全有效。Claude 和 GPT 对中文的理解力已经和英文几乎没有差距。本文所有技巧在中英文 Prompt 上都经过验证。

### Prompt 工程会被淘汰吗？

短期不会，但形态在变化。2026 年的趋势是从"手写 Prompt"转向"用 Skill/规则文件管理 Prompt"。你不再每次手动敲那 200 字上下文，而是让 AI 自动加载你的项目规则。Prompt 工程的核心——结构化表达需求——仍然是人与 AI 高效协作的基础。

### 怎么判断我的 Prompt 好不好？

看 AI 输出的一次可用率。如果 AI 的输出你需要改 30% 以上才能用，说明 Prompt 不够好。目标：AI 输出你只需要微调（10% 以内改动）就能用。如果一次可用率长期低于 70%，逐条检查本文 10 个技巧里漏了哪些。
